# TestBox 需求基线

> 本文件只描述产品要做什么，不描述具体代码实现。
>
> 状态：基线重构完成（2026-08-25）。当前代码是部分可运行实现，不能视为全部需求已经交付。

## 1. 项目目标

TestBox 是一个面向测试工程师的本地测试效能工具箱。它要把分散的测试辅助能力收敛到统一入口，使用户可以：

1. 选择一个测试工具或插件。
2. 填写参数并执行任务。
3. 获得可复现、可追溯的输出文件。
4. 在本地查看任务状态、日志、结果和报告。
5. 在不修改 Core 的情况下增加新的工具插件。

## 2. 产品定位

TestBox 是本地运行、插件化、面向测试工作的 CLI 与桌面 GUI 工具。它不是云端平台、团队协作平台、远程执行平台，也不要求引入服务端或复杂基础设施。

## 3. 目标用户

- 测试工程师
- 自动化测试人员
- 测试开发人员
- 需要临时测试数据、SQL 字段清单或测试证据的研发/测试人员

## 4. 核心使用场景

### 4.1 生成测试数据

用户根据数量、格式、随机种子、模板或字段规则生成模拟数据，用于接口、数据库或 UI 测试。生成结果必须可复现，且不得伪装成真实身份材料。

### 4.2 解析 SQL 字段

用户提供 SQL DDL 文件，获得字段、类型、长度/精度、注释、约束、分区等字段清单。解析器只解析文本，不连接数据库、不执行 SQL。无法识别的内容必须可见地形成警告或失败原因。

### 4.3 生成测试证据

用户可将测试用例与截图整理为可追溯证据报告。当前仓库已经存在 `evidence.inspect` 和 `evidence.build` 实现；是否将其纳入下一阶段最低交付范围，需要确认。

### 4.4 管理任务与插件

用户可以查看可用命令、运行任务、查看历史任务、打开任务工作区、清理过期工作区，并对插件包进行校验、安装、覆盖安装和卸载。

## 5. 功能范围

### 5.1 Core 与 CLI

- 发现本地插件并校验清单。
- 列出可用命令和不可用插件的原因。
- 根据命令 Schema 校验参数。
- 创建独立任务工作区。
- 执行插件并保存日志、结果、报告和输出文件。
- 返回稳定的成功、失败、取消状态和进程退出码。
- 查看任务详情。
- 清理指定日期以前的任务工作区。
- 打包、校验、安装、覆盖安装和卸载插件。

### 5.2 Data Generator

命令：`data.mock`。

最低能力：

- 生成模拟个人信息、手机号等测试数据。
- 支持随机种子。
- 支持 JSON、CSV、XLSX 等已实现或确认的输出格式。
- 支持规则集、SQL DDL、Excel 字段清单和金融模板等规则化输入（以插件 Schema 为准）。
- 唯一性必须显式声明，只在当前任务内保证唯一；容量不足时失败，不静默输出重复值。
- 证件/身份类内容必须明确标识为测试数据，不能用于真实认证。

### 5.3 SQL Parser

命令：`sql.parse`。

最低能力：

- 解析常见 `CREATE TABLE` 定义。
- 提取字段、类型、长度/精度、注释、主键、唯一、外键、自增、默认值和分区等信息（取决于输入方言）。
- 支持仓库测试覆盖的 MySQL、PostgreSQL、SQL Server、Oracle、SQLite 及已实现的相关 DDL 变体。
- 输出 JSON/CSV/XLSX 等插件 Schema 支持的字段清单。
- 支持宽松警告与严格失败两种使用方式。
- 不执行用户提供的 SQL。

### 5.4 Evidence Tool

当前实现包含：

- 从 Excel 测试用例识别待执行项。
- 关联截图与检查点。
- 生成 Word/Excel 等证据输出。

这部分保留为现有能力，但扩展优先级、浏览器自动化范围和最终报告格式为 `NEEDS_CONFIRMATION`。

### 5.5 GUI

GUI 必须是 Core/Runtime 的可视化入口，而不是第二套业务实现。至少需要支持：

- 浏览工具和命令。
- 根据 Schema 填写参数。
- 选择文件输入。
- 执行、取消或等待任务完成。
- 查看任务状态、日志摘要、结果、警告、输出文件和报告。
- 查看任务历史和工作区。
- 查看插件状态、版本、能力和诊断信息。

当前 GUI 仅作为现状参考，不作为视觉资产保护对象，后续允许整体重做。

## 6. 用户主流程

1. 查看工具/插件列表。
2. 选择命令。
3. 查看命令说明和参数要求。
4. 填写参数并进行本地校验。
5. 启动任务。
6. 获取任务 ID，并显示任务状态。
7. 查看结果、警告、日志和输出路径。
8. 需要时打开或导出任务产物。
9. 按生命周期策略清理历史工作区。

CLI 与 GUI 必须使用相同的 Runtime、插件清单、Schema 和结果模型。

## 7. 业务规则与约束

- 插件之间不得直接调用或共享内部实现；跨插件能力必须经 Core 协调。
- 插件只能通过稳定 SDK 使用任务目录、配置、日志和输出能力。
- 输入文件在任务边界内处理，并记录来源与哈希（当前代码对 Schema 声明的文件输入进行暂存）。
- 输出文件必须位于任务 `output/` 内，结果只能声明相对路径。
- 参数、任务清单、日志和报告不得泄露密码、令牌、连接串等敏感值。
- SQL、脚本和未知插件代码不应被当作可信输入执行；当前 V1 插件仍属于本地可信插件，清单校验不等于操作系统安全沙箱。
- 不提供云端同步、多人协作、远程执行或插件市场作为当前目标。

## 8. 非功能要求

- 本地 CLI 冷启动目标为 3 秒以内；实际基准需在目标机器上测量。
- 单次生成 100,000 条测试数据是目标规模，不能据此承诺所有插件都达到相同吞吐量。
- 相同插件版本、参数、输入和随机种子应产生可复现结果。
- 失败任务必须保留足以诊断的结构化错误和任务工作区。
- 插件故障、超时或进程异常不得使 Core 进程整体崩溃。
- 输出和日志大小必须有上限或可配置限制。

## 9. 当前版本基线

### 已在当前代码中观察到

- Python 包、CLI 入口和可选 PySide6 GUI。
- 本地插件发现与 `manifest.yaml` 校验。
- Plugin Host 子进程执行。
- 任务工作区、SQLite 任务历史、结果 JSON 和 Markdown 报告。
- `data.mock`、`sql.parse`、`evidence.inspect`、`evidence.build` 命令。
- 插件包打包、安装、覆盖安装和卸载。
- 集成测试覆盖 Core、Data Generator、SQL Parser 和部分 Evidence Tool 流程。

### 当前最低交付建议

优先稳定以下闭环，再扩大功能：

1. Core/CLI 插件发现。
2. `data.mock` 可复现生成。
3. `sql.parse` 字段清单输出。
4. 任务追踪、结果和工作区。
5. 可重做的 GUI 基础入口。

Evidence Tool、Excel Tool、Env Check、AI 插件、插件市场等作为后续能力，不在本轮基线中扩张。

## 10. Out of Scope

- 云端数据库、云端任务队列和远程插件执行。
- 多用户账号、登录、团队权限和在线协作。
- Kubernetes、微服务、消息队列等基础设施。
- 任意 SQL 执行、数据库连接代理或生产数据同步。
- 真实个人信息、真实身份证件或可通过真实认证的材料生成。
- 本轮直接重写业务代码或实现新的 GUI。

## 11. 验收标准

| 类别 | 验收标准 |
| --- | --- |
| 发现 | 无效插件不能阻塞有效插件；用户能看到无效原因。 |
| 执行 | 合法命令能接收 Schema 参数并返回结构化成功/失败结果。 |
| 可追溯 | 每次任务有唯一 ID、工作区、脱敏参数、结果、报告和输出路径。 |
| 可复现 | 相同版本、输入、参数和 seed 的生成任务结果一致。 |
| 安全 | 不把密钥写入日志/历史；身份类模拟产物有明确测试标识。 |
| 失败处理 | 参数错误、输入错误、插件异常、超时都能给出可理解的错误摘要。 |
| GUI | GUI 显示的任务状态和结果必须来自同一 Runtime，而不是复制业务逻辑。 |
| 回归 | Core、Data Generator、SQL Parser 的现有自动化测试持续通过。 |

## 12. Open Questions

以下问题不影响本轮知识库初始化，但进入正式实现前需要确认：

1. Evidence Tool 是否提升为下一阶段 P0/P1，还是仅保持兼容维护？
2. GUI 首要支持平台是 macOS、Windows，还是两者同等优先？
3. 是否需要真正的实时进度/日志流和任务取消；若不需要，是否保持当前一次请求/一次响应的简单 Host 协议？
4. 是否允许插件安装第三方依赖并为每个插件创建独立虚拟环境？当前代码没有实现完整的隔离环境安装流程。
5. 是否保留 `typer`、`pydantic`、`loguru` 作为正式依赖？当前实现主要使用 `argparse`、标准库和部分 PyYAML 能力。
6. GUI 是否需要插件启用/禁用、权限确认和设置页面；这些在旧 UI 规范中被提出，但当前代码尚未实现。

## 13. 状态定义

- `COMMITTED`：产品方向和验收要求已纳入基线。
- `IMPLEMENTED`：当前代码中已观察到对应能力。
- `PARTIAL`：有实现或测试，但未达到完整目标。
- `NEEDS_CONFIRMATION`：需要产品或架构决策后才能进入正式实现。

本文件中的“当前版本基线”同时区分产品目标和代码现状，不能将 `IMPLEMENTED` 自动理解为最终产品已验收。
