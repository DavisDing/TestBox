# 本地安全审计修复与系统隔离、签名发布方案

日期：2026-10-24。适用范围：本轮用户提供的 5 项高风险和 10 项中风险发现。

## 1. 范围与验收口径

本轮直接修复当前架构中的确定性缺陷，并交付系统沙箱与签名发布方案。后两项是用户授权的**设计交付**，不是已安装、启用或完成目标系统验收的功能。当前插件继续按可信本地代码运行；安装确认、环境过滤、进程组和路径检查均不提供恶意代码安全隔离。

验收依据是当前源码和隔离临时目录中的行为回归。源码、Qt offscreen、合成更新包不能代替 Windows 原生安装器、冻结 Host、真实桌面截图或发布签名链验收。没有修改远端发布设置、创建密钥、安装新依赖或发布任何版本。

## 3. 系统沙箱：目标与契约（PROPOSED）

### 3.1 威胁模型

目标是运行恶意 Python 与本地扩展时，仍由操作系统强制约束文件、网络、进程、内存和 CPU。阻止其读取用户主目录、云凭据、父进程环境和其他任务，阻止写出当前任务输出、访问未经授权的网络或留下脱离生命周期的进程。发布者签名只证明来源，不授予更多权限。

同一用户主动修改 TestBox 二进制、内核漏洞、管理员绕过不属于首版威胁模型。当前版本没有任何这些系统隔离保证，不能只加 Python audit hook、重写 open/import、虚拟环境或事后扫描后改称 sandboxed。

### 3.2 运行模型

引入平台 `HostLauncher`，提供可信兼容模式与真正受限模式，输出明确的 `isolation_mode`、后端、策略版本和不可用原因。受限模式不可用时必须在加载插件入口前失败，不得自动降级为可信模式。是否把第三方默认改为受限、如何允许用户主动选择可信兼容，是产品迁移决定（NEEDS_CONFIRMATION）。

Core 在任务启动前复制输入和插件包，按实际内容哈希固定快照，再创建沙箱。Core/历史库、用户插件目录、信任根和其他任务不暴露给插件；插件目录、Python 运行时和依赖只读；本任务 input 只读；output 允许写，独立临时空间按任务销毁。日志/结果通过有界专用通道交给 Core；不把整个 workspace 可写地挂载给插件。

默认无网络、无新子进程、无屏幕/剪贴板/浏览器/桌面会话访问。输入和导出均由 Core 执行；插件不能把用户传入的任意绝对路径当作权限授予。文件名、链接、大小、类型和产物登记仍在 Core 校验，防止沙箱内路径与宿主路径混用。

现有 capabilities 不能直接成为可信授权。建立版本化权限 Schema 和 Core 白名单：包声明能力，用户授权上限，Core 计算最小交集。权限增大必须重新确认；包/签名/策略变化使旧授权失效。授权绑定插件摘要、发布者身份和策略版本，不能只绑定可伪造的插件名。

### 3.3 平台方案

| 平台 | 候选实现 | 必须验证的条件 |
| --- | --- | --- |
| Windows | 独立原生 launcher；AppContainer/受限 token 与最小 ACL；Job Object 限制内存/CPU/进程数、禁止 breakaway、关闭时终止；受限创建后、恢复运行前完成 Job 分配 | Python/Qt 冻结运行时能从只读位置加载；Job 嵌套与宿主 runner 兼容；创建到 Job 分配无插件执行窗口；网络 loopback、命名管道、链接与用户目录拒绝 |
| Linux | bubblewrap 的独立用户/挂载/PID/网络 namespace，配合 seccomp 和 cgroup v2；可评估 Landlock 作为额外文件访问限制 | user namespace/cgroup 授权是否可用；受限主机和容器中的后端不可用必须失败；系统库与依赖只读最小挂载；网络/进程/内存限制由宿主配置强制 |
| macOS | 独立签名且带最小 App Sandbox 权限的原生 helper/XPC 服务，Core broker 传递输入与输出句柄；避免继承桌面主程序的宽权限 | PyInstaller/Python/动态扩展签名与加载兼容；读写句柄授权正确；用户 home、Apple Events、网络、子进程和截图访问拒绝；是否需要容器/VM 后端评估 |

这些是实施候选，不是本机可用性结论。现有 Web 检索在本环境返回错误，公共站点 DNS 也不可用；平台 API 与发行条件必须在实施前以官方文档及原生原型重新核实。不得把过期、不可分发的接口或 shell 包装器作为安全承诺。

### 3.4 资源与兼容

候选默认资源预算：内存 512 MiB、CPU 时间 120s、墙钟沿用 300s、最大产物 500 MiB、独立临时区 256 MiB、默认最多 1 个进程；正式阈值需用 9 个官方插件基准测量后确认。内存/进程/临时区配额必须由 OS 强制，不只在任务结束检查；POSIX setrlimit 不能替代所有平台的整个进程树配额。

evidence.build 的桌面交互需要屏幕权限，不应赋给任意第三方 Python。优先保留受信任的官方截图 broker，让沙箱仅消费截图副本并生成文件；若首版无法做到，明确将交互 Evidence 标为可信兼容模式。默认转换所有现有插件前，必须验证可选依赖、截图、字体和系统库；不以删除功能通过验收。

### 3.5 系统隔离验收

必须在每个目标 OS 运行黑盒插件：读取沙箱外合成 secret/父环境、写入输出外、符号链接/硬链接、网络 DNS/loopback、启动子孙/脱离树、异常退出、超时取消、内存/CPU/临时空间耗尽、日志洪泛。只用合成凭据，不测试真实用户秘密。

验收同时要求外部访问被 OS 拒绝、其他任务和 Core 可用、拒绝原因可见、取消/超时后所有受管进程与临时资源释放。检测到后端缺失、策略安装失败、句柄授权失败即不加载插件。源码或 mock 验证不能将该项状态改为通过。

## 4. 插件签名（PROPOSED）

本地第三方包先继续依赖明确的信任确认，不伪装成官方认证。后续插件签名清单应绑定稳定 plugin ID、版本、Core 兼容范围、权限 Schema 版本、每个包内文件的路径/大小/摘要以及包整体摘要；验证来源身份后再预览并安装同一份快照，避免预览到安装间替换。

发布者信任根由程序内置或独立可信管理流程加入，绝不从该 ZIP 自带的公钥自我认证。GUI 展示发布者、密钥 ID、验证状态和权限变化。未知密钥/撤销/摘要不符拒绝“已签名可信”标识；允许安装未签名包时，仍需明确的本地代码信任动作。签名与 sandboxed 分别展示，不能互相代替。

## 5. 应用签名发布与更新（PROPOSED）

### 5.1 信任链与元数据

建议采用维护中的 TUF 实现与 Ed25519，避免自写密码学或把下载清单附带的公钥当信任根。候选依赖为 python-tuf、securesystemslib 及其受支持密码学后端；确切版本、冻结体积、目标 Python/Windows 兼容性在原型阶段核实并锁定（NEEDS_CONFIRMATION），本轮没有安装或声明这些依赖。

四类元数据分别负责：离线 root 固定角色和阈值；targets 绑定 CLI/GUI 目标包、大小、摘要、组件、目标版本和增量基线；snapshot 固定元数据版本组合；timestamp 提供有期限的新鲜度。客户端持久记录已见版本，检查签名、阈值、有效期、版本单调性和目标绑定，拒绝回滚、重放、混合清单及冻结元数据。

更新器和完整安装器内置初始 root；运行参数不能更换信任根，`--manifest-url` 只可作为镜像位置选择，不能改变发布者信任。离线 `--package` 路径也必须有同一可信元数据链，不能绕过验签。命令中的 `--force` 只能重试同版本，不能跳过签名、有效期、组件、基线或回滚保护。

### 5.2 密钥与 CI

建议 root 使用 2-of-3 离线阈值，发布 targets 与在线短期 timestamp 分权。具体密钥保管者、有效期、紧急轮换/撤销责任人由维护者确认；私钥不入库、不写插件环境、不放可被 PR 读取的构建产物或日志。

CI 的普通测试和可执行构建与签名发布分离；PR 不接触签名权限。受保护发布环境先检查测试与原生验收，再签 targets/snapshot/timestamp 并发布不可变目标。客户端下载的包、包内清单与签名 targets 三方绑定。Authenticode 对 Windows 安装器/更新器的系统发布者身份提供独立保证；不能用 ZIP 内 SHA-256 代替签名元数据。

签名认证必须在下载/解包/变更安装内容的适当边界前完成，之后继续执行现有路径、组件、哈希、基线、备份和恢复检查。更新器自身的替换需完整安装器或单独经过签名验证的引导流程；不移除当前“更新包不得管理 updater”保护。

### 5.3 迁移与失效处理

现有 unsigned 更新器没有可远程证明的新信任根。首次启用验签应由用户安装经独立可信渠道获取的完整签名安装器，内置 root 并迁移本地版本状态；不能让旧 unsigned 链自行下载一把公钥后宣称供应链已可信。

缺签、未知密钥、过期、篡改、错误组件/基线、版本回退、时间异常均明确失败；网络离线保留当前安装和恢复材料，不自动放行未验证包。恢复事务日志不能授予新的更新权限；先恢复本地既有事务，再验证新目标。旧版无日志的半更新不猜测修复或删除未知文件。

### 5.4 验收

用独立测试密钥验证正确签名、错误密钥、1 字节篡改、过期 timestamp、回放旧版本、混合 snapshot/targets、CLI/GUI 交叉包、离线绕过、密钥轮换/撤销、丢失签名服务和 HTTPS 降级。真发布验收须由维护者配置真实信任根和受保护签名流程，并验证下载的正式产物，不能用测试密钥结果冒充生产信任链完成。

## 6. 实施顺序与待确认决策

1. 本轮直接修复与回归收敛，记录未关闭的安全边界。
2. Windows 首先完成 AppContainer/Job 与冻结 Host 原型；另外两平台各自验证候选后端，不承诺一个 Python 包实现跨平台沙箱。
3. 维护者确认 root 保管与首次可信安装方式；验证 TUF 库/冻结兼容，锁定依赖，实施签名构建和强制验证。
4. 原生黑盒验收通过后再迁移第三方默认执行模式；将“可信代码”和“系统隔离”在 Runtime/GUI/CLI 状态中区分。

需要维护者决定的只有：默认执行模式迁移、三平台支持顺序/分发方式、资源预算、Evidence broker 的范围，以及密钥保管和首次信任根分发。当前实现不因这些待定项自动扩展为沙箱或正式签名发布。
